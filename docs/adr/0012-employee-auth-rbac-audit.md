# ADR-0012: Admin identity and permissions — email Employees, mandatory TOTP with step-up, seeded-RBAC editor, middleware audit log

The legacy back-office was weaker than the member front: unsalted `MD5(password+serverKey)` for admins (members at least got salt), image captcha + SMS-OTP as the only second factor, no TOTP, no lockout, a 7-day rememberMe cookie under a hardcoded cipher key, an unpermissioned reset-password endpoint, and a magic `root` username bypassing all checks (`AdminRealm.java:69`). Its RBAC — ~190 permission strings over three tables with editor pages — was never used to differentiate anyone: of 6 seeded roles (mostly `test`/`aaa` junk), only the super-admin role had grants. And the ticket's assumption that `data_dictionary` drove the admin sidebar was wrong: the sidebar is the login response's permission tree intersected client-side with a hardcoded route table (`04_Web_Admin/src/router/router.js:80-160`); `data_dictionary` is a generic KV store. We decided: **employees are email+argon2id accounts with mandatory TOTP at login and a fresh TOTP step-up on fund-moving actions; the RBAC tables and grant editor are ported but the permission catalog is code-seeded and read-only; one generic audit log is written by middleware for every mutation and auth event.**

## Decision

- **Employee** (the glossary term; `admin` stays reserved for the service/app/page names): login identifier is **email**, password argon2id, exactly one **Role**, one `enabled` flag (legacy's duplicate `enable`/`status` pair dies, as do qq/avatar). Internal provisioning by a super-admin — no employee email-verification flow. Legacy dead weight that must not carry over: unsalted MD5, image captcha, SMS-OTP admin login, rememberMe cookie, `root` username bypass, the unguarded reset-password endpoint, `department` (already dropped in the context map).
- **Authentication**: opaque httpOnly-cookie session rows in Postgres (same mechanic as members, ADR-0006), **12 h absolute + 30 min idle** expiry, no remember-me; **5 failed logins → 15 min per-account lockout**; no captcha (lockout + rate limits, per ADR-0006's stance). **TOTP is mandatory for every employee** — the people who can move funds get the factor members only need for withdrawals. A **Step-up** (fresh TOTP code at action time, replacing legacy's login-password re-auth in `ExchangeCoinController:237` & co.) is required for: manual balance adjust, member TOTP reset, withdrawal approval, hot→cold transfer, failed broadcast/sweep retry, code-channel credentials save, employee create, and resetting another employee's password or TOTP.
- **Permission model — full RBAC port with a code-seeded catalog**: `admin_role`, `admin_permission`, `admin_role_permission` survive as admin-api tables; each Employee holds exactly one Role (`role_id` FK — legacy's shape, not M2M); enforcement is server-side per-endpoint permission-string middleware in admin-api (legacy's one genuinely good idea, `@RequiresPermissions`), **resolved per request** with the grant cache invalidated on role edits — a revoked grant bites on the next request, mid-session. The **permission catalog itself is seeded idempotently from the endpoint list and read-only in the UI**: a permission string exists because a Go handler checks it, so UI-invented or renamed strings would silently gate nothing. The editor edits **grants** (role→permission), not permissions. Internal admin RPCs to wallet/exchange/api stay unauthenticated on the compose network (context map + ADR-0007): admin-api is the sole permission gate.
- **Roles**: four seeded — **super-admin, finance, compliance, support** — with grants per the resolution matrix on ticket #17: finance owns funds (adjust, withdrawal audit, Wallet Ops retry/pause, hot↔cold), compliance owns identity (KYC review, member TOTP reset), support owns member view/lock + announcements/help content, super-admin adds coin/Market config, code channels, employee management, and everything read-side incl. engine status (ADR-0010's internal status RPC view, visible to all roles) and the audit log (super-admin/finance/compliance). Guards: seeded roles have editable grants but cannot be deleted; a role in use by any employee cannot be deleted; employee management refuses self-disable, self-role-removal, and disabling/locking the last enabled super-admin.
- **Menus**: the Nuxt admin app keeps a **static route table** (the `findSlideArr` port) keyed by permission string; the sidebar derives from the employee's live permission set returned at login; the server middleware is the only real gate. No server-driven menu tree, no `data_dictionary` involvement.
- **Audit log**: one append-only admin-api table — employee, action (`verb:resource`), target id, before/after JSON, origin IP, timestamp — **written by middleware for every mutating admin endpoint plus login/logout/lockout events**, replacing both legacy's annotation-opt-in `admin_access_log` (whose gaps are how the reset-password hole went unlogged) and serving ADR-0009's deferred market-edit audit trail and ADR-0006's "audit-logged" member TOTP resets.
- **Bootstrap**: the ADR-0007 installer creates the first super-admin from generated one-time credentials printed at install; first login forces password change + TOTP enrollment before anything else. Break-glass for a locked-out sole super-admin is a host-side CLI reset command (documented runbook; audit-logged as a system actor).

## Considered options (rejected)

- **Fixed roles in code, no RBAC tables** (the recommended option in session): rejected by the owner — the grant editor is wanted for operating reality beyond v1's four roles. The code-seeded read-only catalog is the containment: editor flexibility on grants, zero ability to desynchronize the catalog from the code that enforces it.
- **Role checks only, no permission strings**: rejected — couples every handler to the role list; adding a role means touching every endpoint.
- **Full permission CRUD** (legacy `PermissionController` parity): rejected — UI-invented strings gate nothing and renames silently break gating.
- **Multiple roles per employee**: rejected — micro-mixes make "who could do X?" unanswerable from the audit log; the matrix needs exactly one hat per person.
- **TOTP login without step-up**: rejected — a stolen session can approve withdrawals and move funds to cold for its full 12 h lifetime.
- **Password re-auth as step-up** (legacy mechanic): rejected — the session thief already has the password.
- **Legacy captcha + SMS-OTP admin login**: rejected — drags an SMS provider through admin login even when no code channel is activated, and the stack has no Redis.
- **Member-parity sliding 7-day sessions**: rejected — long-lived staff sessions with fund-moving power are exactly the thing worth avoiding.
- **Grants cached until re-login** (legacy EhCache behavior): rejected — revocation must be immediate when the audit log shows misuse.
- **Annotation-opt-in or per-domain audit logs**: rejected — opt-in guarantees gaps (legacy's demonstrated failure mode); per-domain trails scatter "who changed what" across schemas.
- **Manual seed SQL bootstrap**: rejected — error-prone hash/TOTP formats, no forced rotation. **Env-file standing password**: rejected — a standing secret on disk.
- **Username identifier / glossary term "Admin"**: rejected — a second namespace for nothing; "admin" is already overloaded three ways (admin-api, admin app, admin pages), and legacy itself logs in via `/system/employee/sign/in`.

## Consequences

- admin-api's table list from the context map changes: `admin_access_log` is replaced by the audit log table; `admin`, `admin_role`, `admin_permission`, `admin_role_permission` stand.
- The admin surface list (~views over members, KYC, withdrawals, Wallet Ops, coin/Market config, code channels, content, employees, roles, engine status, audit log) now has its permission/step-up/audit envelope fully assigned; page layouts and endpoint shapes are `/to-spec` work, not further decisions.
- Forced first-login rotation means the installer's printed credentials are single-use; the break-glass CLI becomes the documented exception path, not a routine one.
- Losing the sole super-admin's TOTP with no other super-admin is an operator error with a known recovery cost (host access + runbook); the employee-management guards make it hard to cause from inside the UI.
